# Technical plan: Wialon integration, ролі доступу, сповіщення
### Transpak — платформа управління автопарком

---

## 1. Інтеграція з Wialon API

### 1.1 Що таке Wialon у цій системі
Wialon — це джерело телеметрії (GPS-трекери на вантажівках), а не система обліку бізнесу. Він знає координати, одометр, рух/стоянку, показники з датчиків (якщо встановлені). Він **не знає** про графік ТО, ваших водіїв як сутність кадрового обліку, ролі користувачів чи маршрути в бізнес-розумінні. Тому Wialon — постачальник даних, а вся бізнес-логіка (статуси ТО, звіти, ролі) залишається у власній БД Transpak.

### 1.2 Автентифікація
Wialon Remote API працює через токен доступу (генерується в Wialon Hosting → «Записи» → «Токени доступу»):

1. Отримати токен (довгостроковий, з обмеженим набором дозволів — лише читання даних одиниць).
2. Виконати `token/login` → отримати `sid` (session id), дійсний до завершення сесії.
3. Усі подальші запити йдуть з цим `sid`.

**Рекомендація**: токен зберігати в змінних середовища бекенду (не в коді, не в БД у відкритому вигляді), сесію Wialon оновлювати автоматично при 401.

### 1.3 Які дані та якими методами тягнути

| Дані | Метод Wialon API | Періодичність |
|---|---|---|
| Список ТЗ (units) | `core/search_items` (`itemsType: avl_unit`) | раз на день (зміни рідкісні) |
| Поточне положення / рух-стоянка | `unit/get_position` або push-повідомлення (Events API) | кожні 1–5 хв |
| Одометр (пробіг) | лічильник `counters` у властивостях unit (`unit/get_unit_data` або звіт) | кожні 15–30 хв |
| Пробіг за період (день/тиждень/місяць) | Wialon Reports API — готовий звіт «Mileage» за unit за діапазон дат | за запитом користувача + нічна агрегація |
| Рівень / витрата пального | сенсор `fuel level` на unit, якщо фізично встановлений | кожні 15–30 хв |
| Маршрути / геозони (частi напрямки) | `resource/get_zone_data` + аналіз треків, або власна класифікація за початковою/кінцевою точкою рейсу | нічна агрегація |

**Важливо**: якщо на вантажівках немає паливних датчиків, Wialon фактичну витрату не дасть — тоді розділ «Паливо» показує норматив і оцінку за пробігом, а не факт. Це варто уточнити технічно на етапі обстеження парку.

### 1.4 Архітектура синхронізації

```
Wialon API  →  Sync-service (cron / worker)  →  Transpak DB  →  Backend API  →  Frontend
```

- **Sync-service** — окремий процес (Node.js або Python), що:
  - раз на 15–30 хв опитує Wialon за списком unit + одометр + статус руху;
  - раз на добу тягне детальні звіти (mileage за день, паливо) і кладе в таблиці історії;
  - при отриманні нового одометра — перераховує «пробіг з останнього ТО» і генерує подію, якщо перетнуто поріг (наближається / прострочено).
- **Transpak DB** зберігає: власні сутності (ТЗ, водії, ТО-записи, користувачі, ролі), а також кеш телеметрії (одометр, статус, дата останньої синхронізації) — щоб дашборд не залежав від доступності Wialon у реальному часі.
- **Мапінг**: таблиця `truck.wialon_unit_id`, яку адміністратор заповнює один раз при додаванні ТЗ (обрати зі списку unit-ів Wialon).

### 1.5 Обробка збоїв
- Якщо Wialon недоступний — дашборд показує останні відомі дані з позначкою «оновлено о [час]», без падіння інтерфейсу.
- Логувати помилки синхронізації окремо, з алертом адміністратору при повторних збоях (> 3 підряд).

## 2. Ролі доступу

### 2.1 Модель
Дві ролі на старті — розширювана структура (легко додати «механік», «диспетчер» пізніше):

| Роль | Права |
|---|---|
| **Адміністратор** | Повний CRUD: додавання/редагування/видалення ТЗ, водіїв, записів ТО; позначення ТО виконаним; керування користувачами та їх ролями; налаштування сповіщень |
| **Переглядач** | Тільки перегляд усіх розділів (дашборд, автопарк, ТО, водії, маршрути, паливо); без кнопок редагування, без API-доступу до мутуючих ендпоінтів |

### 2.2 Реалізація
- Автентифікація — JWT (або сесійні токени), у payload — `user_id`, `role`.
- **Backend**: кожен мутуючий ендпоінт (`POST/PUT/DELETE`) перевіряє роль через middleware — переглядачу повертається `403`, навіть якщо запит підроблено напряму, без фронтенду.
- **Frontend**: приховує кнопки редагування/додавання за роллю (як у прототипі — клас `admin-only`), але це лише UX-зручність, не захист.
- Створення користувачів і призначення ролей — доступне тільки адміністратору, в окремому розділі «Користувачі» (у прототипі поки не реалізовано — додати наступним кроком).

## 3. Сповіщення

### 3.1 Події, що генерують сповіщення
- ТО наближається (поріг, наприклад 1500 км або 3 дні — налаштовується)
- ТО прострочено
- ТЗ переведено в ремонт / повернувся з ремонту
- Wialon тривалий час не надає дані по ТЗ (можлива несправність трекера)

### 3.2 Архітектура
```
Sync-service / бізнес-логіка
        │
        ▼
  Notification service  ──►  Таблиця notifications (у платформі, дзвіночок)
        │
        └────────────────►  Telegram Bot API  ──►  chat_id користувача
```

- **Одна подія — два канали виводу**, без дублювання логіки: сервіс сповіщень записує подію в БД (для дзвіночка в інтерфейсі) і паралельно шле повідомлення в Telegram, якщо користувач підключив бота.
- **Прив'язка Telegram**: у профілі користувача — кнопка «Підключити Telegram» → генерується одноразовий код → користувач надсилає його боту командою `/start CODE` → бот зберігає `chat_id` у профілі користувача в Transpak DB.
- **Telegram-бот** — окремий легкий сервіс (Node.js `node-telegram-bot-api` або Python `python-telegram-bot`), слухає команду `/start`, інакше лише розсилає — двостороннього діалогу не потрібно.
- Налаштування частоти/типів сповіщень (наприклад, тільки прострочені ТО, не «наближається») — на розсуд адміністратора в розділі налаштувань.

## 4. Пропонований стек (орієнтовно)

| Компонент | Варіант |
|---|---|
| Backend API | Node.js (NestJS/Express) або Python (FastAPI) |
| БД | PostgreSQL |
| Sync-service | окремий воркер, той самий стек що й backend, запуск через cron / BullMQ / Celery |
| Telegram-бот | окремий процес, спільна БД з backend |
| Frontend | те, що вже в прототипі — можна довести до React/Vue |
| Автентифікація | JWT + refresh token |

## 5. Модель технічного обслуговування (уточнено)

«ТО» — не одна подія, а набір незалежних регламентних робіт з різними інтервалами (колодки, масло/фільтри, шини, ремінь ГРМ тощо), плюс окремо ремонти. Тому схема БД:

| Таблиця | Призначення |
|---|---|
| `maintenance_type` | Довідник видів робіт: назва, інтервал у км (`interval_km`, nullable), інтервал у днях (`interval_days`, nullable), поріг "наближається" для кожного. Приклади: масло/фільтри (км + час), колодки (лише км), шини (лише км), плановий тех.огляд (лише час) |
| `truck_maintenance_status` | Для кожної пари (ТЗ, вид робіт): пробіг/дата останнього виконання → звідси розраховується залишок і статус (ок / наближається / прострочено) |
| `maintenance_log` | Історія виконаних робіт: ТЗ, вид робіт, дата, пробіг на момент виконання, хто виконав, вартість |
| `repair` | Окремо від регламенту: тип (`planned` / `unplanned`), опис, дата, простій (днів), вартість, статус (в процесі / завершено) |

**Статус ТЗ загалом** (для бейджа в списку автопарку) — найгірший статус серед усіх його позицій регламенту: якщо хоч одна прострочена — ТЗ показується як «прострочено», з зазначенням, яка саме позиція є причиною.

**Логіка Wialon у цьому контексті**: одометр і дата з Wialon — вхідні дані для розрахунку залишку по кожній позиції reglamentu (км) і для дій, прив'язаних до часу (дні). Сам регламент, довідник видів робіт і історія виконання — виключно бізнес-дані Transpak, Wialon про них нічого не знає.

## 6. Наступні кроки
1. Отримати тестовий доступ до Wialon API (токен) і перевірити, які саме дані фактично доступні по вашому парку (особливо — чи є паливні датчики).
2. Узгодити фінальний перелік видів регламентних робіт та їхні інтервали (це краще звірити з механіком — цифри в прототипі orientировочні).
3. Спроєктувати повну схему БД (truck, driver, maintenance_type, truck_maintenance_status, maintenance_log, repair, user, notification, route_log).
4. Реалізувати sync-service окремо від UI — можна протестувати на 2–3 реальних ТЗ до повного розгортання.
5. Розгорнути Telegram-бота та механізм прив'язки акаунтів.
6. Додати розділ «Користувачі» в адмін-частину інтерфейсу.
