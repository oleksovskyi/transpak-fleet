# Transpak Fleet — вказівки для Claude Code

## Що це за проєкт
Платформа управління автопарком для транспортної компанії Transpak (30 вантажівок).
Керівник/механік бачить статуси ТЗ, регламентне ТО (кожен вид робіт має власний
інтервал у км і/або днях, з можливим індивідуальним винятком по конкретному ТЗ),
ремонти (планові/позапланові), пробіг за період, закріплення водіїв, найчастіші
маршрути, витрату пального. Дані про телеметрію (одометр, рух/стоянка, паливо)
надходять з Wialon API.

**Перед будь-якою роботою прочитай:**
- `docs/wialon-integration-plan.md` — технічний план інтеграції з Wialon, ролі, сповіщення, схема БД
- `docs/transpak-dashboard-reference.html` — робочий HTML-макет інтерфейсу з тестовими даними (відкрий у браузері, щоб побачити всі екрани й логіку). Це референс вигляду й функціоналу, не фінальний код фронтенду.

## Структура репозиторію
```
backend/        Node.js API + Prisma (PostgreSQL)
frontend/       клієнтський застосунок
sync-service/   воркер синхронізації з Wialon API (окремий процес)
docs/           технічна документація і design-референс
```

## Ключові бізнес-правила (не спрощувати без узгодження)
- ТО — НЕ одна дата. Це каталог `maintenance_type` (масло/фільтри, колодки, шини, ремінь ГРМ, тех.огляд тощо), кожен зі своїм інтервалом у км і/або днях. Статус ТЗ = найгірший статус серед усіх його позицій.
- Інтервали редагуються адміністратором через UI (таблиця `maintenance_type`), НІКОЛИ не хардкодяться в коді.
- Для видів робіт з `allow_override = true` адміністратор може задати індивідуальний інтервал для конкретного ТЗ (`truck_maintenance_override`), який має пріоритет над загальним значенням.
- Ремонти (`repair`, planned/unplanned) — окрема сутність від регламентного ТО.
- Дві ролі: `admin` (повний CRUD) і `viewer` (тільки читання). Перевірка ролі — обов'язково на бекенді (middleware), фронтенд лише ховає кнопки для UX.
- Wialon — джерело телеметрії (одометр, GPS-статус, паливо за наявності датчиків), НЕ джерело бізнес-даних (ТО, водії, ролі). Синхронізація йде через окремий `sync-service`, а не напряму з фронтенду чи бекенду.

## Стиль роботи
- Одна задача за раз (одна таблиця, один ендпоінт, один компонент). Не генерувати весь застосунок одним промптом.
- Після зміни схеми БД — показати diff міграції перед застосуванням.
- Дизайн: строгий корпоративний стиль, сині/сірі тони (див. CSS-змінні у `docs/transpak-dashboard-reference.html` як орієнтир палітри).
- Мова інтерфейсу і коментарів у бізнес-логіці — українська (як у макеті); імена змінних/функцій у коді — англійською.
